# AI 개발 역할 분담

Oct 19, 2026 · @Yumin Jung

**6명이 Agent를 하나씩 맡아 만듭니다.** 누가 어떤 역할을 맡을지, 일정을 어떻게 할지 정합니다.

## 1. 지금까지 된 것

여러 Agent가 같이 쓰는 부분(공통부)은 main에 들어가 있습니다. **아래는 직접 만들지 말고 가져다 씁니다.**

| 이미 있는 것 | 쓰는 법 |
| --- | --- |
| AI 모델 부르기 | `llm.structured(...)` 한 줄로 부릅니다. 호출 기록은 자동으로 남습니다 |
| 도구를 골라 가며 확인하는 AI (도구 루프) | `llm.tool_agent(...)`. Root의 분석 질문에만 씁니다. 호출 기록, 도구 결과 감싸기, 호출 횟수 상한이 자동으로 붙습니다 |
| 백엔드와 주고받는 데이터 형식 | `contract.py`에서 가져옵니다 (지원자, 공고, 회사, 분석 결과) |
| 테스트용 가짜 모델 | `FakeLlm`. 실제 모델 없이 테스트합니다. 도구 호출은 `ToolCall`로 흉내 냅니다 |
| 가상 지원자 8명 | `sample_applicants`. 지원자별 정답은 `ai/tests/samples/README.md` |
| 차별 조건 막기 | `blocked_attribute`. 나이·성별 같은 조건이면 정해진 문구로 거절합니다 |
| 근거 문장 확인 | `verified_evidence`. 원문에 없는 근거는 버립니다 |
| 제출 문서 안전하게 넣기 | `document_block`. 문서 속 지시문을 따르지 않게 합니다 |
| DB 연결 | `SessionDep`. 테이블은 `db.base.Base`를 상속합니다 |
| 백엔드에서 AI 서버 부르기 | `AiServerClient`. 내 Agent만 켜고 끄는 설정도 있습니다 |

자세한 규칙은 AGENTS.md의 ai/ 부분에 있습니다.

## 2. 역할 분담

6명이 역할을 하나씩 맡습니다. **각자 원래 맡은 Agent가 들어 있는 역할을 고르면** 기존 분담에서 크게 바뀌지 않습니다.

| # | 역할 | 하는 일 (한 줄) | 담당 |
| --- | --- | --- | --- |
| 1 | Root Agent | Chat 요청을 이해하고 무엇을 할지 계획합니다 |  |
| 2 | 지원서 분석 | 제출 서류를 읽고 요약, 서류 점수, 공고 조건 대조를 만듭니다 |  |
| 3 | 프로필·검색 | 분석 결과를 지원자 프로필로 저장하고, 조건으로 지원자를 찾습니다 |  |
| 4 | 면접 | 맞춤 면접 질문을 만들고, 면접 답변을 정리합니다 |  |
| 5 | 평가·리포트 | 평가 결과를 해석하고, 채용이 끝나면 최종 리포트를 씁니다 |  |
| 6 | 공고·안내 | 공고 수정안과 결과 안내 메일 초안을 씁니다 |  |

## 3. 이렇게 나눈 이유

**같은 일을 두 번 하지 않고, 같은 파일을 두 사람이 고치지 않고, 서로 기다리지 않게 나눴습니다.**

### 판단 근거

1. **겹치는 일은 공통부로 한 번만 만들었습니다.**
   - 모델 호출과 도구 루프, 데이터 형식, DB, 차별 조건 차단을 6명이 각자 만들면 같은 일을 6번 하고, 방식이 제각각이라 합칠 때 다시 맞춰야 합니다.
   - 공통부가 있으니 각자는 자기 Agent의 프롬프트와 로직에만 시간을 씁니다.
2. **폴더 단위로 나눠 같은 파일을 고칠 일이 거의 없습니다.**
   - 역할마다 자기 Agent 폴더와 자기 백엔드 `Remote` 클래스만 고칩니다.
   - 여러 사람이 같이 고치는 곳은 `main.py`의 라우터 등록 한 줄뿐입니다.
3. **기존에 맡은 Agent를 그대로 살렸습니다.**
   - 역할은 이미 맡은 Agent를 묶은 것이라 새로 익힐 범위가 작습니다.
   - 어제까지 만든 맛보기 코드를 이어서 쓸 수 있습니다.
4. **비슷한 일끼리 묶었습니다.**
   - 공고·안내: 둘 다 "양식 + 요청 → 수정안"을 만드는 같은 모양입니다.
   - 면접: 질문 생성과 답변 분석이 같은 면접 전형 자료를 씁니다.
   - 평가·리포트: 둘 다 전형 결과를 읽고 정리하는 일입니다.
   - 지원서 분석: 두 연결 모두 같은 입력(지원자 + 공고)을 받습니다.
5. **서로 기다리지 않습니다.**
   - 다른 Agent가 없어도 가짜 응답(stub)과 가상 지원자로 혼자 끝까지 만들고 테스트할 수 있습니다.
   - Agent마다 따로 켜는 설정이 있어서 내 것만 실제로 연결해 확인합니다.
6. **AI 서버와 백엔드 연결을 한 사람이 맡습니다.**
   - 요청·응답 형식을 혼자 맞추고 바로 확인하니, 다른 사람에게 넘기고 기다리는 시간이 없습니다.
7. **실수는 자동 검사가 잡습니다.**
   - 데이터 형식이 한쪽만 바뀌거나 DB 마이그레이션이 두 갈래로 갈라지면 CI가 실패합니다.

### 역할별 일의 양

| 역할 | 기존 백엔드 연결 | 새로 만들 연결 | 무게가 실린 곳 |
| --- | --- | --- | --- |
| 1 Root Agent | 1 | 0 | 요청 판단 프롬프트를 가장 많이 다듬어야 함 |
| 2 지원서 분석 | 2 | 0 | 서류 점수와 조건 대조의 정확도 |
| 3 프로필·검색 | 0 | 0 | 프로필 테이블 설계와 검색 도구 |
| 4 면접 | 1 | 1 | 답변 분석용 백엔드 데이터 형식 |
| 5 평가·리포트 | 1 | 1 | 결과표·파일·URL 처리 |
| 6 공고·안내 | 2 | 0 | 고정 칸과 필수 문구 보존 |

연결 수가 적은 역할은 프롬프트나 설계에 무게가 있도록 묶었습니다.

### 다른 방법과 비교

| 방법 | 결과 |
| --- | --- |
| 각자 처음부터 따로 만들기 | 같은 기능을 6번 만들고, 합칠 때 형식이 달라 충돌합니다 |
| 화면(기능 흐름)별로 나누기 | 한 Agent를 여러 사람이 고치게 되고, 공통 부분은 맡을 사람이 없습니다 |
| **Agent 폴더별로 나누기 (선택)** | 고치는 파일이 겹치지 않고, 각자 혼자 끝까지 확인할 수 있습니다 |

## 4. 역할별 세부 내용

역할마다 AI 서버 쪽과 백엔드 연결까지 한 사람이 끝까지 맡습니다. 위치는 `ai/src/hiremate_ai/` 기준입니다.

### 1) Root Agent

- **하는 일**: Chat 요청을 받아 대상 확인 → 요청 종류 판단(찾기, 분석, 편집, 되묻기, 차단) → 실행 계획을 만듭니다. (FR-12\~17)
  - 찾기는 같은 질문에 같은 후보가 나오도록 검색 도구를 정해진 순서로 씁니다.
  - 분석 질문은 `llm.tool_agent`로 프로필, 원문, 전형 결과, 분석 Agent를 골라 가며 근거를 모읍니다. 서류와 과제를 같이 봐야 하는 질문이 여기에 해당합니다.
  - 편집은 명령으로만 바꿉니다.
- **위치**: `agents/root/`
- **백엔드 연결**: `POST /agents/root/plan` ← `RootAgent.plan`. 결과는 `ChatPlan`입니다.
- **주의**: 지원자를 직접 고르거나 상태를 바꾸지 않고 계획만 돌려줍니다. 백엔드의 `StubRootAgent`가 기대 동작을 보여 주는 예시입니다. 흐름은 LangGraph로 짜고, 그래프를 만드는 함수는 `LlmClient`를 인자로 받습니다. 조회 범위(기업·채용·전형)는 도구 인자가 아니라 `ToolAgent.run(context=...)`으로 넣습니다.

### 2) 지원서 분석

- **하는 일**: 제출 서류를 읽고 요약과 서류 점수를 만듭니다. 지원자를 공고 조건과 하나씩 맞춰 봅니다. (FR-08, 17, 19)
- **위치**: `agents/analysis/application/`
- **백엔드 연결**: `POST /agents/application/analyze` ← `ApplicationAgent.analyze`, `POST /agents/candidate-analyst/analyze` ← `CandidateAnalyst.analyze`
- **주의**: 근거는 원문에 있는 문장만 씁니다. 문서 속 지시문은 따르지 않습니다(가상 지원자 6번). 본문이 빈 문서는 "확인 필요"로 둡니다(7번).

### 3) 프로필·검색

- **하는 일**: 분석 결과(항목, 근거 문장, 출처)를 지원자 프로필로 저장하고, "금융 경험자" 같은 조건으로 지원자를 찾는 도구를 만듭니다. (FR-08, 13, 14)
- **위치**: `db/`(프로필 테이블), `tools/`(검색 도구)
- **백엔드 연결**: 없습니다. Root와 분석 역할이 이 도구를 씁니다.
- **주의**: 프로필 테이블은 여러 역할이 같이 쓰므로 첫 버전을 먼저 정해 공유합니다. 검색은 항상 현재 기업·채용·전형 안에서만 합니다. 나이·성별 같은 항목은 저장하지 않습니다. 도구는 `@tool`을 단 async 함수로 만들고 범위는 `ToolRuntime`의 context로 받습니다. 그래야 Root의 도구 루프에 그대로 넣을 수 있습니다.

### 4) 면접

- **하는 일**: 이전 전형의 근거로 맞춤 면접 질문을 만들고(FR-27), 면접 답변에서 확인된 것과 확인 안 된 것을 정리합니다(FR-28).
- **위치**: `agents/generation/interview/`, `agents/analysis/interview/`
- **백엔드 연결**: 질문은 `POST /agents/interview/questions` ← `InterviewAgent.questions`. 답변 분석은 백엔드에 부르는 곳이 없어서 새로 만듭니다.
- **주의**: 답변 분석은 백엔드가 보낼 데이터 형식부터 정합니다.

### 5) 평가·리포트

- **하는 일**: 평가 결과표(CSV·XLSX)와 과제 제출물을 해석하고(FR-26), 채용이 끝나면 전형별 인원, 합격 근거, 특이사항을 정리한 최종 리포트를 씁니다(FR-31).
- **위치**: `agents/analysis/assessment/`, `agents/generation/report/`
- **백엔드 연결**: 리포트는 `POST /agents/report/write` ← `ReportAgent.write`. 평가 해석은 백엔드에 부르는 곳이 없어서 새로 만듭니다.
- **주의**: 제출 URL을 가져올 때 내부망 주소는 막습니다. 리포트의 인원과 숫자는 백엔드 값을 그대로 쓰고 AI가 만들지 않습니다.

### 6) 공고·안내

- **하는 일**: 담당자 요청대로 공고 수정안을 만들고(FR-02\~04), 전형 결과 안내 메일 초안을 씁니다(FR-29).
- **위치**: `agents/generation/posting/`, `agents/generation/communication/`
- **백엔드 연결**: `POST /agents/posting/revise` ← `PostingAgent.revise`, `POST /agents/communication/write` ← `CommunicationAgent.write`
- **주의**: 수정안만 만들고 게시·발송은 하지 않습니다. 고정 칸과 필수 문구는 바꾸지 않습니다. 요청이 모호하면 되묻습니다.

## 5. 만드는 순서

역할이 달라도 순서는 모두 같습니다. **AI 서버 쪽과 백엔드 연결을 PR 하나로 올립니다.**

1. **브랜치 만들기**
   - main을 받고 `feat/<이슈번호>-<설명>` 브랜치를 만듭니다.
2. **AI 서버 쪽 만들기**
   - 라우터: `POST /agents/<키>/<메서드>`. 요청은 백엔드 메서드의 매개변수 이름을 키로 한 JSON, 응답은 반환 타입 그대로입니다.
   - 로직: 모델은 `llm.structured(...)`로 부릅니다. 도구를 골라 가며 확인해야 하는 Root의 분석 질문만 `llm.tool_agent(...)`를 씁니다. `create_agent`나 `ChatOpenAI`를 직접 쓰지 않습니다.
   - 다른 Agent(주로 Root)가 부를 기능은 패키지 최상위에 async 함수로 공개합니다. Agent끼리 HTTP로 부르지 않습니다.
   - `main.py`에는 라우터 등록 한 줄만 더합니다.
3. **테스트**
   - `FakeLlm`과 가상 지원자로 테스트를 짭니다. 기대 결과는 지원자별 정답표를 따릅니다.
4. **백엔드 연결**
   - `backend/.../ai/infra`에 `Remote` 클래스를 만들고 `@ConditionalOnAiMode(agent = ..., mode = AiMode.REMOTE)`를 답니다. AI 서버는 `AiServerClient`로만 부릅니다.
   - 로컬에서 내 Agent만 켜서 끝까지 확인합니다 (예: `HIREMATE_AI_AGENTS_ROOT=remote`). 다른 Agent는 지금처럼 가짜 응답(stub)으로 동작합니다.
5. **검사 → PR → 머지**
   - backend `./gradlew check`, ai `uv run ruff check && uv run ruff format --check && uv run mypy && uv run pytest`
   - CI가 모두 통과하면 작성자가 Rebase and merge 합니다. 브랜치는 하루이틀 안에 머지합니다.
