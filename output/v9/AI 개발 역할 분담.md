# AI 개발 역할 분담

Oct 29, 2026 · @Yumin Jung

**6명이 Agent를 하나씩 맡아 만듭니다.** 누가 어떤 역할을 맡는지, 각 역할이 어디를 고치고 무엇을 지켜야 하는지 정합니다.

## 1. 함께 쓰는 것

여러 Agent가 같이 쓰는 부분(공통부)은 main에 들어가 있습니다. **아래는 직접 만들지 말고 가져다 씁니다.**

| 공통부 | 쓰는 법 |
| --- | --- |
| AI 모델 부르기 | `llm.structured(...)` 한 줄로 부릅니다. 호출 기록(`ai.llm_calls`)은 자동으로 남습니다 |
| 도구를 골라 가며 확인하는 AI (도구 루프) | `llm.tool_agent(...)`. Root의 계획(종류별 형식 `forms`만)과 분석 루프에만 씁니다. 호출 기록, 도구 결과 감싸기, 호출 횟수 상한이 자동으로 붙습니다 |
| 요청 하나의 호출 예산 | `new_model_call_budget`, `using_model_call_budget`. Root와 하위 Agent가 같은 예산을 나눠 씁니다 |
| 백엔드와 주고받는 데이터 형식 | `contract.py`에서 가져옵니다 (지원자, 공고, 회사, 분석 결과, 판정, 확인 상태) |
| 작업 대기열과 AI 워커 | 화면이 기다리지 않는 일은 백엔드가 Redis 대기열에 넣고 워커가 처리합니다. 작업 유형은 `worker/handlers.py`의 표에 더하고, 다시 해도 같은 실패는 `PermanentError`로 알립니다 |
| 테스트용 가짜 모델 | `FakeLlm`. 실제 모델 없이 테스트합니다. 도구 호출은 `ToolCall`로 흉내 냅니다 |
| 가상 지원자 | `sample_applicants`. 지원자별 정답은 `ai/tests/samples/README.md` |
| 차별 조건 막기 | `blocked_attribute`. 나이·성별 같은 조건이면 정해진 문구로 거절합니다 |
| 근거 문장 확인 | `verified_evidence`, `evidence_source`. 원문에 없는 근거는 버립니다 |
| 제출 문서 안전하게 넣기 | `document_block`, `data_block`과 `UNTRUSTED_RULE`. 문서 속 지시문을 따르지 않게 합니다 |
| NCS 자료 | `tools/ncs.py`. 능력단위, 수행준거, 중요도·활용도 조사 점수를 공고, 서류 평가, 면접이 같이 씁니다 |
| 지원자 프로필 | `db/` 테이블, `tools/profile_search.py`(찾기), `tools/profile_lookup.py`(읽기). 항목마다 근거, 출처, 확인 상태가 있습니다 |
| DB 연결 | `SessionDep`, 테스트는 `db_session`. 테이블은 `db.base.Base`를 상속하고 `ai` 스키마에 둡니다 |
| 백엔드에서 AI 서버 부르기 | `AiServerClient`. Agent마다 stub과 remote를 따로 켜고 끕니다 |
| 실행 추적 | `LANGSMITH_TRACING=true`면 요청 하나, 워커 작업 하나가 기록 하나로 남습니다. 가상 지원자로 개발할 때만 켭니다. Root 그래프는 `uv run langgraph dev`로 Studio에서 봅니다 |

자세한 규칙은 AGENTS.md의 ai/ 부분에 있습니다.

## 2. 역할 분담

6명이 역할을 하나씩 맡습니다. **각자 원래 맡은 Agent가 들어 있는 역할을 고르면** 기존 분담에서 크게 바뀌지 않습니다.

| # | 역할 | 하는 일 (한 줄) | 담당 |
| --- | --- | --- | --- |
| 1 | Root Agent | Chat 요청을 계획하고 처리기·분석 루프로 실행한 뒤 근거를 검토합니다 |  |
| 2 | 지원서 분석 | 제출 서류를 공고 기준으로 판정하고 서류 점수와 프로필을 만듭니다 |  |
| 3 | 프로필·검색 | 분석 결과를 지원자 프로필로 저장하고, 조건으로 지원자를 찾습니다 |  |
| 4 | 면접 | 맞춤 면접 질문을 만들고, 면접 답변을 정리합니다 |  |
| 5 | 평가·리포트 | 평가 결과를 해석하고, 채용이 끝나면 최종 리포트를 씁니다 |  |
| 6 | 공고·안내 | 공고·포스터 수정안과 결과 안내 메일 초안을 씁니다 |  |

## 3. 이렇게 나눈 이유

**같은 일을 두 번 하지 않고, 같은 파일을 두 사람이 고치지 않고, 서로 기다리지 않게 나눴습니다.**

### 판단 근거

1. **겹치는 일은 공통부로 한 번만 만들었습니다.**
   - 모델 호출과 도구 루프, 호출 예산, 데이터 형식, 대기열, DB, 차별 조건 차단을 6명이 각자 만들면 같은 일을 6번 하고, 방식이 제각각이라 합칠 때 다시 맞춰야 합니다.
   - 공통부가 있으니 각자는 자기 Agent의 프롬프트와 로직에만 시간을 씁니다.
2. **폴더 단위로 나눠 같은 파일을 고칠 일이 거의 없습니다.**
   - 역할마다 자기 Agent 폴더와 자기 백엔드 `Remote` 클래스만 고칩니다.
   - 여러 사람이 같이 고치는 곳은 `main.py`의 라우터 등록 한 줄과 `worker/handlers.py`의 작업 표 한 줄뿐입니다.
3. **맡은 Agent를 그대로 살렸습니다.**
   - 역할은 이미 맡은 Agent를 묶은 것이라 새로 익힐 범위가 작습니다.
4. **비슷한 일끼리 묶었습니다.**
   - 공고·안내: 둘 다 "양식 + 요청 → 수정안"을 만드는 같은 모양입니다.
   - 면접: 질문 생성과 답변 분석이 같은 면접 전형 자료를 씁니다.
   - 평가·리포트: 둘 다 전형 결과를 읽고 정리하는 일입니다.
   - 지원서 분석: 두 연결 모두 같은 입력(지원자 + 공고 + 평가 기준)을 받습니다.
5. **서로 기다리지 않습니다.**
   - 다른 Agent가 없어도 가짜 응답(stub)과 가상 지원자로 혼자 끝까지 만들고 테스트할 수 있습니다.
   - Agent마다 따로 켜는 설정이 있어서 내 것만 실제로 연결해 확인합니다.
6. **AI 서버와 백엔드 연결을 한 사람이 맡습니다.**
   - 요청·응답 형식을 혼자 맞추고 바로 확인하니, 다른 사람에게 넘기고 기다리는 시간이 없습니다.
7. **실수는 자동 검사가 잡습니다.**
   - 데이터 형식이 한쪽만 바뀌면 `contract/` 샘플 왕복 테스트가, DB 마이그레이션이 두 갈래로 갈라지면 Alembic 헤드 검사가 실패합니다.

### 역할별 연결과 무게

| 역할 | 백엔드 연결 | 대기열 작업 | 무게가 실린 곳 |
| --- | --- | --- | --- |
| 1 Root Agent | 1 (+ 대화 기록 4) | 0 | 계획 프롬프트, 대상 범위, 근거 검토 |
| 2 지원서 분석 | 2 | 1 | 판정 정확도, 확인 필요와 보류 처리 |
| 3 프로필·검색 | 1 | 0 | 확인 상태, 같은 입력에 같은 검색 결과 |
| 4 면접 | 2 | 2 | 질문 우선순위와 근거, 답변 분석 |
| 5 평가·리포트 | 2 | 2 | 결과표 매핑, 숫자는 백엔드 값 그대로 |
| 6 공고·안내 | 3 | 0 | NCS 근거, 고정 칸과 필수 문구 보존 |

연결 수가 적은 역할은 프롬프트나 설계에 무게가 있도록 묶었습니다.

### 다른 방법과 비교

| 방법 | 결과 |
| --- | --- |
| 각자 처음부터 따로 만들기 | 같은 기능을 6번 만들고, 합칠 때 형식이 달라 충돌합니다 |
| 화면(기능 흐름)별로 나누기 | 한 Agent를 여러 사람이 고치게 되고, 공통 부분은 맡을 사람이 없습니다 |
| **Agent 폴더별로 나누기 (선택)** | 고치는 파일이 겹치지 않고, 각자 혼자 끝까지 확인할 수 있습니다 |

## 4. 역할별 세부 내용

역할마다 AI 서버 쪽과 백엔드 연결까지 한 사람이 끝까지 맡습니다. 위치는 `ai/src/hiremate_ai/` 기준입니다.

### 1) Root Agent

- **하는 일**: Chat 요청을 받아 차단 확인 → 계획 → 처리 → 근거 검토 → 기록 순서로 답합니다. (FR-12\~17, FR-37)
  - 계획은 모델 한 번으로 요청 종류(find, answer, questions, edit, conversation, clarify, blocked, decision)와 대상 범위(`scope`)를 정합니다. 실제 지원자 목록은 코드가 펼칩니다.
  - 찾기, 편집, 일반 대화, 되묻기, 차단, 결정 안내는 정해진 처리기(`handlers.py`)가, 분석과 확인할 점이 필요한 면접 질문만 좁은 분석 루프(`analysis.py`)가 처리합니다.
  - 분석 루프의 근거에는 번호를 붙이고(`ledger.py`), 근거 검토(`review.py`)가 항목 상태를 근거의 최고 상태 이하로 맞춥니다.
- **위치**: `agents/root/`
- **백엔드 연결**: `POST /agents/root/plan` ← `RootAgent.plan`. SSE로 `status`, `item`을 먼저 보내고 마지막 `done`에 `ChatPlan`을 담습니다. 대화 기록은 `/history`, `/applied`, `/forget`, `/forgetStage`입니다.
- **주의**: 지원자를 직접 고르거나 상태를 바꾸지 않고 계획만 돌려줍니다. 원문을 직접 해석하지 않고 분석 Agent가 저장한 결과를 읽습니다. 낱말 정규식으로 모델의 의도와 대상을 다시 해석하지 않습니다. 그래프 갈래 함수의 반환 타입에는 갈 수 있는 노드를 `Literal`로 적습니다.

### 2) 지원서 분석

- **하는 일**: 제출 서류에서 사실과 본인 역할을 뽑고, 공고의 자격요건·우대사항 항목마다 충족·부분 충족·미충족·확인 필요로 판정합니다. 점수는 코드가 계산합니다(자격요건 50점 + 우대사항 50점, 확인 필요가 남으면 보류). 자기소개서 문항별 요약도 만듭니다. (FR-08, 17, 19, 38)
- **위치**: `agents/analysis/application/`
- **백엔드 연결**: 대기열 작업 `application/analyze`, `POST /agents/application/analyze` ← `ApplicationAgent.analyze`, `POST /agents/candidate-analyst/analyze` ← `CandidateAnalyst.analyze`. Root는 `review_application_documents`를 함수로 부릅니다.
- **주의**: 근거는 원문에 있는 문장만 씁니다. 문서 속 지시문은 따르지 않습니다(가상 지원자 6번). 본문이 빈 문서는 "확인 필요"로 둡니다(7번). 팀 성과나 역할이 불분명한 사실은 프로필에 미확인으로 저장합니다. 모델은 점수를 정하지 않습니다.

### 3) 프로필·검색

- **하는 일**: 분석 결과(항목, 근거 문장, 출처, 확인 상태)를 지원자 프로필로 저장하고, "금융 경험자" 같은 조건으로 지원자를 찾는 도구를 만듭니다. 지원자 카드의 프로필 탭도 이 데이터를 읽습니다. (FR-08, 11, 13, 14)
- **위치**: `db/`(프로필 테이블), `tools/`(검색·조회 도구), `api/profile.py`
- **백엔드 연결**: `POST /agents/profile/read` (카드 프로필 탭). Root와 분석 역할이 검색·조회 도구를 씁니다.
- **주의**: 검색은 항상 현재 기업·채용·전형 안에서만 합니다. 같은 입력에는 같은 순서로 돌려줍니다. 확인 필요, 미확인, 상충 항목은 찾기의 근거로 쓰지 않습니다. 나이·성별 같은 항목은 저장하지 않습니다. 도구는 `@tool`을 단 async 함수로 만들고 범위는 `ToolRuntime`의 context로 받습니다.

### 4) 면접

- **하는 일**: 이전 전형의 근거로 맞춤 면접 질문을 만들고(FR-27), 면접 답변에서 확인된 것과 확인 안 된 것을 정리합니다(FR-28). 1차는 자기소개 + 핵심 3개, 최종은 자기소개 + 자리 5개입니다. 질문마다 유형과 근거를 남깁니다.
- **위치**: `agents/generation/interview/`, `agents/analysis/interview/`
- **백엔드 연결**: 질문은 대기열 작업 `interview/questions`(결과 확정 때)와 `POST /agents/interview/questions` ← `InterviewAgent.questions`(Chat 요청). 답변 분석은 대기열 작업 `interview-analyst/analyze`와 `POST /agents/interview-analyst/analyze`. Root는 `analyze_interview`를 함수로 부릅니다.
- **주의**: 같은 공고의 지원자에게 같은 우선순위를 적용합니다. 차별 조건, 점수·내부 판단 노출, 중복은 코드가 검사합니다. 답변 분석은 합격·불합격 의견이나 점수를 만들지 않습니다.

### 5) 평가·리포트

- **하는 일**: 평가 결과표(CSV·XLSX)와 과제 제출물, 평가 메모를 해석하고(FR-26), 채용이 끝나면 전형별 인원, 합격 근거, 특이사항을 정리한 최종 리포트를 씁니다(FR-31).
- **위치**: `agents/analysis/assessment/`, `agents/generation/report/`
- **백엔드 연결**: 대기열 작업 `assessment/analyze`, `report/write`. 같은 경로의 `POST /agents/assessment/analyze`, `POST /agents/report/write`도 있습니다.
- **주의**: 제출 URL을 가져올 때 내부망 주소는 막습니다. 점수·등급은 모델에게 보여 주지 않고 바꾸지 않습니다. 리포트의 인원과 숫자는 백엔드 값을 그대로 쓰고 AI가 만들지 않습니다. 약점과 미확인 점은 강점처럼 쓰지 않고 특이사항으로 둡니다.

### 6) 공고·안내

- **하는 일**: 담당자 요청대로 공고 칸별 수정안과 포스터 디자인 추천을 만들고(FR-02\~04, 33), 전형 결과 안내 메일 초안을 씁니다(FR-29). 자격요건·우대사항은 NCS 능력단위를 근거로 씁니다.
- **위치**: `agents/generation/posting/`, `agents/generation/communication/`
- **백엔드 연결**: `POST /agents/posting/revise` ← `PostingAgent.revise`, `POST /agents/posting/design` ← 포스터 디자인, `POST /agents/communication/write` ← `CommunicationAgent.write`
- **주의**: 수정안만 만들고 게시·발송은 하지 않습니다. 바뀐 칸은 원래 공고와 비교해 코드가 정합니다. 고정 칸과 필수 문구는 바꾸지 않습니다. 요청이 모호하거나 전형 종류를 알 수 없으면 되묻습니다. 포스터는 공고 내용을 바꾸지 않습니다. 안내에는 지어낸 평가나 전형별 안내와 맞지 않는 일정을 넣지 않습니다.

## 5. 만드는 순서

역할이 달라도 순서는 모두 같습니다. **AI 서버 쪽과 백엔드 연결을 PR 하나로 올립니다.**

1. **브랜치 만들기**
   - main을 받고 `feat/<이슈번호>-<설명>` 브랜치를 만듭니다.
2. **AI 서버 쪽 만들기**
   - 라우터: `POST /agents/<키>/<메서드>`. 요청은 백엔드 메서드의 매개변수 이름을 키로 한 JSON, 응답은 반환 타입 그대로입니다.
   - 로직: 모델은 `llm.structured(...)`로 부릅니다. 도구를 골라 가며 확인해야 하는 Root의 분석 루프만 `llm.tool_agent(...)`를 씁니다. `create_agent`나 `ChatOpenAI`를 직접 쓰지 않습니다.
   - 다른 Agent(주로 Root)가 부를 기능은 패키지 최상위에 async 함수로 공개합니다. Agent끼리 HTTP로 부르지 않습니다.
   - 화면이 기다리지 않는 일이면 `worker/handlers.py`의 표에 같은 이름의 작업 유형을 더합니다.
   - `main.py`에는 라우터 등록 한 줄만 더합니다.
3. **테스트**
   - `FakeLlm`과 가상 지원자로 테스트를 짭니다. 기대 결과는 지원자별 정답표를 따릅니다. 테스트는 `tests/` 아래 같은 폴더 구조에 둡니다.
4. **백엔드 연결**
   - `backend/.../ai/infra`에 `Remote` 클래스를 만들고 `@ConditionalOnAiMode(agent = ..., mode = AiMode.REMOTE)`를 답니다. AI 서버는 `AiServerClient`로만 부릅니다.
   - 화면이 기다리지 않는 일은 `job.JobQueue`로 넣고 결과는 `JobFinished` 이벤트로 받아 기록합니다. 실패는 분석 실패로 두어 담당자가 다시 요청할 수 있게 합니다.
   - 로컬에서 내 Agent만 켜서 끝까지 확인합니다 (예: `HIREMATE_AI_AGENTS_ROOT=remote`). 다른 Agent는 가짜 응답(stub)으로 동작합니다.
