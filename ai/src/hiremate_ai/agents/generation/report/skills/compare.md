# 지원자 비교

비교 대상(targets)은 모두 현재 전형 지원자다. 범위가 여러 전형이면 끝난 전형은 확정 기록, 현재 전형은 as_of 기준이다.

## 순서

1. get_overview로 총점 key, 영역(점수 key · 항목 key), 지표(평균 등, 어느 key의 집계인지)를 본다
2. get_values로 대상의 점수와 판정을 읽는다
3. 영역마다 대상끼리 판정이 갈리는 항목을 찾는다. 차이가 없는 영역도 '고르게 충족'이 읽을 점이다
4. focus(요청 관점, 예: 협업)가 있으면 관련 항목을 고르고, get_evidence와 ask_specialist로 그 관점의 근거를 모은다

## 섹션 구성

1. 한눈에 보기
   - rings (영역 점수 표): views마다 영역 점수 key 하나. 화면은 지원자마다 영역별 10칸 막대와 점수, 총점을 한 줄로 그린다. 맨 위에 둔다
   - rings (관점별 항목 충족 표): 항목 판정 key를 관점 3~6개로 묶어 지원자별로 견준다. 화면은 관점마다 충족 항목 수만큼 칸을 채우고 (예: 2/3), 지원자끼리 다른 관점 줄을 강조한다.
     관점마다 항목 2~3개를 항목 이름을 보고 묶는다. 항목 하나짜리 관점은 하나까지다(한 항목이면 0% 아니면 100%라 견줄 것이 적다).
     영역 전체나 '기타'를 한 관점으로 두지 않는다. 예: 협업(코드 리뷰 · 협업 항목), 연동 · API, 품질 · 테스트, 데이터 설계, 요구사항 · 설계.
     있음 · 없음 key 묶음(예: document.skill.*)이 있으면 '보유 기술' 관점도 하나 둔다.
     요청 관점(focus)은 그중 하나이고, 요청 관점만 그리지 않는다.
     관점 묶음은 설계서의 perspectives 칸에 넣어도 된다. 그러면 코드가 관점별 항목 충족 표를 만든다
   - stacked: 대상의 총점을 영역 점수로 쌓은 막대 (자리가 있으면)
2. 영역마다 섹션 하나 (area에 영역 id)
   - bar: 그 영역 점수 key 하나, reference에 그 key의 평균 지표
   - matrix: 그 영역 항목 key 모두 × 대상
3. 전체 안 위치
   - distribution: 총점 key, highlight에 비교 대상, reference에 평균 지표
   - position: 영역 점수가 전형 전체에서 상위 몇 %인지
4. 근거 (늘 둔다)
   - evidence: 대상마다 한 항목. 대상끼리 판정이 갈린 항목과 부분 · 미충족 항목의 근거를 get_evidence로 골라
     keywords와 근거 id를 넣는다. focus(요청 관점)가 있으면 그 관점의 근거를 고른다

## 간략히 요청일 때

요약 두세 문장 + 섹션 하나: 영역 점수 표, 관점별 항목 충족 표, 요청 관점이 있으면 evidence(대상마다 한 항목).
영역 섹션 · 분포 · 판정표는 쓰지 않는다.

## 요약에 담을 것

공통점 한 문장, 차이점(영역 · 항목 기준) 한두 문장, 확인할 점 한 문장. 누가 낫다거나 누구를 뽑으라고 쓰지 않는다.
'가장 높다', '제일'처럼 순위로 읽히는 말 대신 값을 그대로 쓴다. 예: 'A-0036은 우대사항 45점, A-0010 · A-0033은 20점 · 15점이에요.'
'차이가 있어요'처럼 값 없이 흐리게 쓰지 않는다.
