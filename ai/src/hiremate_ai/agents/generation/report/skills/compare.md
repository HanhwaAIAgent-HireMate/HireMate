# 지원자 비교

비교 대상(targets)은 모두 현재 전형 지원자다. 범위가 여러 전형이면 끝난 전형은 확정 기록, 현재 전형은 as_of 기준이다.

## 순서

1. get_overview로 총점 key, 영역(점수 key · 항목 key), 지표(평균 등, 어느 key의 집계인지)를 본다
2. get_values로 대상의 점수와 판정을 읽는다
3. 영역마다 대상끼리 판정이 갈리는 항목을 찾는다. 차이가 없는 영역도 '고르게 충족'이 읽을 점이다
4. focus(요청 관점, 예: 협업)가 있으면 관련 항목을 고르고, get_evidence와 ask_specialist로 그 관점의 근거를 모은다

## 점수가 있는지 먼저 본다

get_overview의 총점 key와 영역 점수 key를 본다. 서류 전형은 점수를 쓰지 않아 총점 key와 영역 점수 key가 없고
항목 판정만 있다. 점수가 없으면 bar · stacked · distribution · position · donut을 쓰지 않는다.
판정 값(충족 · 미충족)은 숫자가 아니라 막대 · 분포로 그릴 수 없고, 항목 판정 key는 지표 id가 아니라 도넛에 넣을 수 없다.

## 섹션 구성 (점수가 없을 때: 서류 전형)

시각화는 rings · matrix · tally 세 종류로 채운다.

1. 한눈에 보기
   - rings (관점별 항목 충족 표): 아래 '관점 묶기'대로 항목 판정 key를 관점 3~6개로 묶는다. 맨 위에 둔다
   - tally (by=applicant): 대상마다 전체 항목의 판정 구성(충족 · 부분 · 미충족 · 보류) 막대. keys에 항목 판정 key 모두
2. 영역마다 섹션 하나 (area에 영역 id)
   - matrix: 그 영역 항목 key 모두 × 대상
   - tally (by=key): 그 영역 항목마다 대상의 충족 비율 (자리가 있으면)
3. 근거 (늘 둔다): 아래 '근거 섹션'

## 섹션 구성 (점수가 있을 때: 평가 · 면접 전형 등)

1. 한눈에 보기
   - rings (영역 점수 표): views마다 영역 점수 key 하나. 화면은 지원자마다 영역별 10칸 막대와 점수, 총점을 한 줄로 그린다. 맨 위에 둔다
   - rings (관점별 항목 충족 표): 항목 판정 key가 있으면 '관점 묶기'대로 묶는다
   - stacked: 대상의 총점을 영역 점수로 쌓은 막대 (자리가 있으면)
2. 영역마다 섹션 하나 (area에 영역 id)
   - bar: 그 영역 점수 key 하나, reference에 그 key의 평균 지표
   - matrix: 그 영역 항목 key 모두 × 대상
3. 전체 안 위치
   - distribution: 총점 key, highlight에 비교 대상, reference에 평균 지표
   - position: 영역 점수가 전형 전체에서 상위 몇 %인지
4. 근거 (늘 둔다): 아래 '근거 섹션'

## 관점 묶기

화면은 관점마다 충족 항목 수만큼 칸을 채우고 (예: 2/3), 지원자끼리 다른 관점 줄을 강조한다.
관점마다 항목 2~3개를 항목 이름을 보고 묶는다. 항목 하나짜리 관점은 하나까지다(한 항목이면 0% 아니면 100%라 견줄 것이 적다).
영역 전체나 '기타'를 한 관점으로 두지 않는다. 예: 협업(코드 리뷰 · 협업 항목), 연동 · API, 품질 · 테스트, 데이터 설계, 요구사항 · 설계.
있음 · 없음 key 묶음(예: document.skill.*)이 있으면 '보유 기술' 관점도 하나 둔다.
요청 관점(focus)은 그중 하나이고, 요청 관점만 그리지 않는다.
관점 묶음은 설계서의 perspectives 칸에 넣어도 된다. 그러면 코드가 관점별 항목 충족 표를 만든다

## 판정이 갈린 이유 (splits)

get_overview의 '판정이 갈린 항목'마다 splits에 하나씩 쓴다 (최대 6개).
- text: 누가 무엇이 달랐는지 한 문장. get_evidence 근거의 '세부'(충족한 부분 · 못 채운 부분 · 확인 필요한 부분 · 역할)를
  읽고 쓴다. 예: 'A-0004는 스키마 설계와 SQL 튜닝이 모두 드러나고, A-0006은 설계만 있고 SQL 작성은 서류에 없어요.'
- evidence: 그 문장의 근거 id (get_evidence로 받은 것만).
- '분석 Agent 확인' 줄은 서류 Agent가 본인 역할 · 수행 범위를 다시 확인한 결과다. 있으면 이유에 반영한다.
- 판정이 같은 항목은 쓰지 않는다. 판정을 다시 매기지 않고, 갈린 까닭만 쓴다.

## 근거 섹션

- evidence: 대상마다 한 항목. 대상을 하나도 빼지 않는다. 대상끼리 판정이 갈린 항목과 부분 · 미충족 항목의 근거를
  get_evidence로 골라 keywords와 근거 id를 넣는다. focus(요청 관점)가 있으면 그 관점의 근거를 고른다.
- 근거 id는 get_evidence가 준 글자 그대로 쓴다 (예: e-A-0006-Q-01). 짐작해서 만들지 않는다.
- 원문(정량)을 원문(서술)보다 먼저 고르고, 서술 근거만 있는 강점은 evidence 스킬대로 약하게 쓴다

## 간략히 요청일 때

요약 두세 문장 + 섹션 하나: 영역 점수 표(점수가 있을 때), 관점별 항목 충족 표, 요청 관점이 있으면 evidence(대상마다 한 항목).
영역 섹션 · 분포 · 판정표는 쓰지 않는다.

## 요약에 담을 것

공통점 한 문장, 차이점(영역 · 항목 기준) 한두 문장, 확인할 점 한 문장. 누가 낫다거나 누구를 뽑으라고 쓰지 않는다.
'가장 높다', '제일'처럼 순위로 읽히는 말 대신 값을 그대로 쓴다. 예: 'A-0036은 우대사항 45점, A-0010 · A-0033은 20점 · 15점이에요.'
판정만 있으면 항목 이름과 판정으로 쓴다. 예: 'A-0006만 Git 코드 리뷰 · 협업이 미충족이에요.'
항목은 코드(Q-01, P-03)만 쓰지 않는다. 읽는 사람은 코드를 외우지 않으므로 항목 이름을 10자 안팎으로 줄여 쓴다
(예: Q-01 'Java 또는 Kotlin 기반 서버 개발 경력 3년 이상' → 'Java · Kotlin 경력', P-04 → 'CI/CD 구성').
코드를 꼭 붙여야 하면 이름 뒤 괄호에 둔다. 예: 'Java · Kotlin 경력(Q-01)'. 여러 항목을 코드로만 늘어놓지 않는다.
비율은 count_values로 센 값만 쓴다. 직접 나눠 계산한 숫자는 쓰지 않는다.
'차이가 있어요'처럼 값 없이 흐리게 쓰지 않는다. 문장은 모두 해요체(~어요 · ~예요)로 쓰고 '~습니다 · ~니다'로 끝내지 않는다.
