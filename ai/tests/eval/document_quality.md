# 지원 문서 정제 품질 평가

이 자료는 모두 인공적으로 작성한 가상 문서다. 실제 지원자의 원문과 모델 자격 증명은 포함하지 않는다. 문서 JSON의 형식과 파서 원문 보존, PDF의 실제 읽기 순서와 구조 품질을 별도로 본다.

기존 모델 결과를 기록한 이후 구조 평가에서 최상위에 있어야 할 블록이 다른 제목 아래에 있어도 통과하던 오류를 수정했다. 이전 결과에는 정제 JSON이 저장되지 않아 새 기준으로 재채점할 수 없다. 아래의 과거 구조 점수는 당시 측정 기록이며 현재 기준의 통과 근거가 아니다.

## 평가 자료와 정답

- `tests/eval/document_quality_gold.py`의 페이지 좌표와 `expected_blocks`가 수작업 정답이다. `reading_order`는 PDF를 사람이 읽을 때의 순서다.
- `tests/samples/document_quality_resume.pdf`는 두 열이다. 좌측 기술 목록을 모두 읽은 뒤 우측 경력을 읽는 것이 정답이다.
- `tests/samples/document_quality_cover_letter.pdf`에는 글자 사이 간격이 큰 제목, 인쇄 줄바꿈, 별도 문단과 꼬리말이 있다.
- `tests/samples/document_quality_portfolio.pdf`는 2페이지이며 목록, 3열 표, 실제 도형, 그림 설명, 코드 예시, 머리말과 꼬리말이 있다.
- `tests/samples/document_quality_korean.pdf`에는 벌어진 한국어 제목, 일반 제목, 줄바꿈된 문장과 꼬리말이 있다. backend PDFBox 파서 출력은 같은 `KOREAN_TEXT_CASE` 정답과 비교한다. 파서 조각에서 시작하는 기존 사례도 독립적으로 남겨 추출 오류와 정제 오류를 분리한다.
- `tests/samples/document_quality_sources.json`은 이 가상 PDF에서 백엔드가 추출한 조각이다. 백엔드 테스트는 블라인드 처리를 적용한 실제 추출 결과와 이 파일, Luna JSON의 출처를 대조한다. 별도 통합 테스트는 같은 세 PDF를 제출해 Luna JSON을 저장하고 색인 요청을 확인한다. AI 검색 테스트는 같은 조각과 JSON을 색인해 원문 조각 및 페이지와 기업 범위를 확인한다. 다른 백엔드 통합 테스트는 가상 지원자의 이름, 학교와 학점을 가린 뒤 저장하는 경로를 검사한다. 이 검사들은 서비스 간 네트워크를 한 번에 연결한 실제 배포 검증은 아니다.
- 생성 PDF 5개 페이지는 렌더링해 눈으로 확인했다. PDF 원본의 도형은 그리기 명령이므로 기존 PDF 파서의 이미지 객체 감지와 다를 수 있다.

## 실행

1. 저장된 PDF를 재생성하려면 `ai` 디렉터리에서 다음 명령을 실행한다. PDF 생성기는 표준 라이브러리만 사용한다.

```bash
PYTHONPATH=tests uv run python -m eval.document_quality_fixtures
```

위 명령은 표준 글꼴을 쓰는 영문 PDF 3건만 재생성한다. 한국어 PDF는 macOS의 `AppleSDGothicNeo-Regular` 글꼴과 CoreGraphics, CoreText를 사용해 아래 명령으로 별도로 재생성한다. OS나 글꼴 버전에 따라 PDF 바이트와 글자 배치가 달라질 수 있으므로 시각 검토와 PDFBox 추출을 다시 실행한다. 생성된 PDF가 저장소에 있어 CI에서는 macOS, Swift 또는 해당 글꼴이 필요하지 않다.

```bash
swift -module-cache-path /tmp/hiremate-swift-cache tests/eval/document_quality_korean.swift
```

2. `backend` 디렉터리에서 실제 `PdfText.parse`와 `ParsedDocument.from`으로 가상 PDF를 읽는다. 이 테스트는 가상 원문 조각만 출력한다. `--rerun`은 Gradle 캐시로 인해 결과 출력이 생략되는 것을 방지한다.

```bash
./gradlew test --tests 'com.hiremate.file.DocumentQualityFixturesTests' --rerun --info > /tmp/document-quality-parser.log 2>&1
```

3. `ai` 디렉터리에서 현재 원문 대체 처리의 기준선을 측정한다.

```bash
PYTHONPATH=tests uv run python -m eval.document_quality_baseline /tmp/document-quality-parser.log
```

다른 정제 결과를 비교하려면 `resume`, `cover_letter`, `portfolio`, `korean`을 키로 한 고정 JSON 객체를 별도 JSON 파일로 준비하고 위 명령에 `--documents <파일>`을 추가한다. `korean_parser_text`를 추가하면 한국어 파서 조각도 함께 평가한다.

4. 실제 모델 평가는 선택 사항이며 가상 자료만 전송한다. 아래 설정 파일은 제자리에서 읽고, 비밀값을 출력하거나 복사하지 않는다. 모델 제공자 호출 비용이 발생할 수 있으며 LangSmith 추적은 끈다.

```bash
LLM_MODEL=gpt-6-luna LANGSMITH_TRACING=false PYTHONPATH=tests uv run python -m eval.document_quality_model_eval /tmp/document-quality-parser.log <설정파일경로> --documents-output /tmp/document-quality-documents.json
```

저장한 가상 정제 JSON은 `--documents /tmp/document-quality-documents.json`으로 다시 평가할 수 있어 평가기 수정 때 모델을 다시 호출할 필요가 없다. 파일에는 가상 문서 내용이 담기며 실제 지원자 자료를 입력하거나 저장하지 않는다. 모델 호출 오류로 문서가 없는 사례가 있으면 재평가 전에 결과를 확인한다.

5. 백엔드의 업로드부터 Redis, AI 워커, DB 색인과 검색까지 한 번에 검증하려면 Docker와 `uv`가 필요하다. `backend` 디렉터리에서 다음 명령을 실행한다.

```bash
HIREMATE_DOCUMENT_WORKER_E2E=1 ./gradlew test --tests com.hiremate.apply.DocumentPipelineIntegrationTests --rerun-tasks
```

백엔드 테스트가 일회용 PostgreSQL과 Redis를 시작하고 테스트 전용 AI 워커를 별도 프로세스로 연결한다. 가상 지원자 이름이 마스킹된 문서 세 건을 대상으로 저장, 현재 버전의 색인 및 기업과 채용 범위 안에서의 출처 검색을 확인한다. 워커는 저장된 Luna 결과를 가상 이름의 마스킹에 맞춰 재생하며 테스트용 임베딩을 쓴다. 실제 모델이나 외부 임베딩 서비스는 호출하지 않는다. 이 검사는 기본 백엔드 검사에서 건너뛰며 위 명령으로 명시적으로 실행한다.

## 판정과 한계

- `source_content_matches`는 공백을 뺀 전체 문자가 파서 원문과 같은 순서인지 검사한다. PDF에서 애초에 빠진 글자와 잘못된 정상 띄어쓰기를 이 검사만으로 입증하지 못한다.
- `source_numeric_matches`는 숫자 경계를 별도로 검사한다. 공백을 모두 없애 숫자 둘을 하나로 만든 경우를 허용하지 않는다.
- `single_space_matches`는 파서 원문에서 글자 사이의 공백이 정확히 한 칸인 위치를 출력에서도 유지했는지 검사한다. 문자가 일치하지 않거나 코드 원문이 생략된 결과는 검증할 수 없어 `null`이다. 이 검사는 추가된 공백, 문단 구분과 여러 칸의 의미를 판정하지 못한다.
- `source_word_matches`는 제목, 문단, 목록 항목, 표의 각 필드와 시각 자료 설명 안에서 원문에 붙어 있던 글자 사이에 공백이 새로 생겼는지 검사한다. 블록이나 표 셀의 경계가 URL 기호를 포함해 원문에서 붙어 있던 문자를 나누는지도 확인한다. 목록의 기호와 내용 경계에서는 붙어 있던 문자와 숫자가 나뉘는지 확인한다. 필드 사이의 의미 관계와 블록 간 문단 관계는 이 검사만으로 판정하지 않는다. 문자가 일치하지 않거나 코드 원문이 생략되면 `null`이다.
- `source_provenance_matches`는 내용 위치에 대응하는 원문 조각 ID와 순서를 검사한다. 알 수 없는 ID는 필수 검사 실패다.
- `pdf_reading_order_matches`는 수작업 읽기 순서의 요소가 출력에서 그 순서로 나타나는지 확인한다. 원문 조각만 있는 한국어 사례는 PDF 순서를 판정하지 않는다.
- `structure_passed`와 `structure_total`은 위 정답에 지정한 제목, 문단 역할과 본문, 목록, 표, 참조 등의 개별 점검 수다. 전체 문서의 보편적 정확도나 통계적 성공률이 아니다.
- 코드 본문은 최종 JSON에서 원본 확인 안내로 대체될 수 있다. 이 경우 JSON만으로 코드 원문 누락과 출처 위치를 완전히 검증할 수 없어 해당 값은 `null`로 표시한다. `null`은 통과가 아니다. 알 수 없는 출처는 즉시 실패다.
- 안전 통과 조건은 문서 종류, 문자와 숫자, 원문의 단일 공백과 제목, 문단, 목록 및 표 필드의 단어 경계 보존, 출처 검사다. 여기에 PDF 읽기 순서와 구조 검사를 별도로 함께 확인해야 하며, 대체 처리 결과를 구조화 성공으로 취급하지 않는다. 검색 품질, 시간과 비용은 별도 보고한다. 아래의 기존 결과 파일은 이 공백 지표를 추가하기 전에 생성했으므로 해당 지표가 없으며, 단일 공백 보존의 독립적인 평가 근거로 사용하지 않는다.
- 이 작은 회귀 표본의 목표는 원문과 숫자 및 출처 오류 0건, 수작업 구조 점검 전 항목 통과, PDF 4건의 실제 읽기 순서 확인, 모델 결과의 원문 대체 0건이다. 코드 참조처럼 자동 판정이 `null`인 항목은 원문과 PDF를 직접 검토하기 전에는 통과로 세지 않는다. 이 목표는 운영 전체의 통계적 품질 목표가 아니다.

## 기준선

2026년 11월 7일, `gpt-6-luna`를 `function_calling`, temperature 0, reasoning effort none으로 각 사례에 한 번씩 호출했다. 기록된 4회 호출은 모두 모델 호출 관점에서 성공했지만, 세 PDF와 한국어 원문 조각 모두 최종 구조 검증에서 실패해 원문 대체 결과가 나왔다. 상세 측정은 `document_quality_model_baseline.json`에 있다. 이는 모델 자체의 일반적인 성공률을 의미하지 않는다.

이후 같은 한국어 정답을 가진 PDF를 추가했다. PDFBox에서 제목과 나머지 네 줄을 예상한 순서로 추출하는 것을 확인했고, 원문 대체 경로의 문자와 출처 검사는 통과했으나 구조 점검은 0 / 4였다. 이 PDF에 대한 개선 전 실제 모델 호출은 수행하지 않았으며 위 네 번의 기존 결과에 포함되지 않는다.

| 사례 | 파서 원문 문자와 출처 | PDF 읽기 순서 | 구조 점검 | 원문 대체 사유 |
| --- | --- | --- | --- | --- |
| 이력서 PDF | 통과 | 실패 | 0 / 7 | 문단 role 누락 |
| 자기소개서 PDF | 통과 | 통과 | 0 / 4 | 문단 role 누락 |
| 포트폴리오 PDF | 통과 | 통과 | 0 / 10 | 정제 결과 검증 ValueError, 세부 원인 미기록 |
| 한국어 파서 조각 | 통과 | PDF 미평가 | 0 / 4 | 문단 role 누락 |

각 사례의 모델 호출은 1회였고, 실행 시간은 각각 3.34초, 2.65초, 3.16초, 1.99초였다. 입력 토큰은 793, 824, 1034, 792이고 출력 토큰은 115, 146, 317, 110이다. 실제 요금과 제공자별 단가는 기록되지 않아 비용은 산출하지 않았다. 단일 실행과 소수의 영문 PDF는 대표성이 없으며, 목표 수치나 모델 선택을 결정할 근거로 삼지 않는다.

## 필수 필드 검증과 재시도 적용 후 비교

같은 날 같은 가상 자료와 파서 출력, function calling, temperature 0, reasoning effort none으로 각 모델을 한 번씩 평가했다. 개선 후 결과는 `document_quality_model_current.json`과 `document_quality_model_sol.json`에 있다. 두 결과 모두 파서 원문 문자와 숫자 및 출처 검사는 통과했지만, 이는 PDF의 모든 내용과 정상 띄어쓰기까지 검증했다는 뜻이 아니다.

| 사례 | GPT-6 Luna 구조 점검 | GPT-6 Sol 구조 점검 | 읽기 순서 |
| --- | --- | --- | --- |
| 이력서 PDF | 3 / 7 | 1 / 7 | 두 모델 모두 실패 |
| 자기소개서 PDF | 4 / 4 | 4 / 4 | 두 모델 모두 통과 |
| 포트폴리오 PDF | 0 / 10 | 0 / 10 | 원문 대체 결과는 통과 |
| 한국어 PDF | 2 / 4 | 3 / 4 | 두 모델 모두 통과 |
| 한국어 파서 조각 | 2 / 4 | 3 / 4 | PDF 미평가 |

각 모델은 포트폴리오에서 두 차례 시도 후 원문 대체로 처리했고 나머지는 각각 한 번 호출해 구조화했다. Sol 포트폴리오는 코드 참조의 원문 검증에서 거부됐다. Luna의 이번 실행에서는 세부 거부 사유를 기록하지 않아 비교할 수 없다. 호출 수와 시간, 토큰은 결과 파일에 있다. 단가는 기록하지 않아 비용을 계산할 수 없다. 각 조건의 단일 실행은 결과의 변동성과 모델의 일반 성능을 추정하기에 부족하므로 운영 모델을 교체하지 않는다. 두 열의 순서는 파서 원문 자체가 섞여 있어 정제 모델만 바꿔서는 이 검증을 통과할 수 없다.

이후 코드 원문 검증이 실패하면 해당 내용을 문단으로 보존하도록 재시도 안내를 보강했다. Sol의 별도 단일 재실행에서는 포트폴리오가 두 번의 호출 뒤 구조화됐고 문자, 숫자와 출처 검사는 통과했으며 구조 점검은 8 / 10이었다. 시각 자료 참조와 코드 참조는 정답과 달랐다. 나머지 사례는 위 Sol 결과와 같은 점수였다. 결과는 `document_quality_model_sol_retry.json`에 있다. 재평가 중 표 셀을 연결하면서 서로 다른 숫자를 하나로 합치던 평가기 오류를 발견해 수정하고 테스트했다. 수정 전 재실행의 숫자 점수는 폐기했으며 새 실행 결과로 보고한다. 표본이 적어 대체율이 안정적으로 개선됐다고 단정하지 않는다.

이어서 원문에서 글자 사이에 공백이 정확히 한 칸인 곳을 모델이 붙여 쓰면 거부하도록 검증을 보강했다. 여러 칸의 자간과 줄바꿈은 여전히 정리할 수 있다. 한 칸씩 벌어진 제목도 보호하므로 자동으로 붙이지 못할 수 있고, 삽입된 공백이나 문단 경계의 의미가 올바른지는 보장하지 않는다. 이 검증 적용 후 프롬프트에 같은 지침을 추가하기 전의 단일 실행 결과는 `document_quality_model_luna_spacing.json`, `document_quality_model_sol_spacing.json`이다. 두 모델 모두 포트폴리오를 두 번째 호출에 구조화하고 구조 점검 8 / 10을 받았다. 두 열 이력서의 읽기 순서는 여전히 실패했다.

프롬프트에도 공백 보존 지침을 추가한 뒤의 단일 실행은 `document_quality_model_luna_final.json`, `document_quality_model_sol_final.json`에 있다. Luna는 다섯 사례를 구조화했고 Sol은 자기소개서 한 건을 원문 대체했다. Sol이 자기소개서 제목의 한 칸씩 벌어진 영문 자간을 두 번 붙여 쓰려 해 검증에 거부된 사례다. 이 사례는 정상 공백 보존과 자간 정리의 모호성이 실제 대체 저장으로 이어짐을 보여 준다. 포트폴리오 구조 점검은 Luna 7 / 10, Sol 8 / 10이며 두 열 이력서의 읽기 순서는 두 모델 모두 실패했다. 이 결과를 품질 목표 달성으로 취급하지 않는다.

한 칸 공백을 제거해 재시도할 때 제목 자간도 보존하라고 안내한 후 Sol을 한 번 더 평가했다. 자기소개서는 두 번째 호출에 구조화돼 구조 점검 4 / 4를 통과했고 제목의 한 칸씩 벌어진 공백은 그대로 남았다. 포트폴리오도 두 번 호출해 8 / 10이었고, 이력서 읽기 순서는 실패했다. 결과는 `document_quality_model_sol_space_retry.json`이다. 안내의 효과와 대체율은 단일 실행만으로 확정할 수 없다.

이후 사용자 지시에 따라 실제 모델 호출은 GPT-6 Luna만 사용한다. 최종 재시도 안내를 적용한 Luna의 단일 실행은 `document_quality_model_luna_only.json`에 있다. 다섯 사례 모두 구조화됐고 이력서 1 / 7, 자기소개서 4 / 4, 포트폴리오 8 / 10, 한국어 PDF와 한국어 파서 조각 각각 3 / 4였다. 포트폴리오는 재시도했고 두 열 이력서의 읽기 순서는 실패했다. 앞선 다른 모델 결과는 이 지시 이전에 수행한 가상 자료 실험 이력이다.

## 수정된 평가기의 Luna 실행

2026년 11월 7일 GPT-6 Luna만 사용해 가상 사례를 각각 한 번 실행했다. 검증된 가상 JSON은 `document_quality_luna_documents.json`, 당시 점수와 호출 내역은 `document_quality_luna_verified.json`에 보관한다. 이후 단어 중간에 공백을 삽입하는 오류 검사를 추가하고 같은 JSON을 모델 호출 없이 다시 평가한 결과는 `document_quality_luna_rescored.json`이다. 다섯 사례가 모두 구조화됐고 포트폴리오에서 한 번 재시도해 총 6회 호출됐다. 입력은 6,838토큰, 출력은 1,215토큰이다. [공식 일반 요금](https://developers.openai.com/api/docs/models/gpt-6-luna)의 입력 100만 토큰당 0.10달러와 출력 100만 토큰당 0.50달러를 할인 없이 적용한 추정치는 약 0.0013달러이며 실제 청구액은 확인하지 못했다.

| 사례 | 문자, 숫자, 단일 공백과 출처 | PDF 읽기 순서 | 지정 구조 점검 |
| --- | --- | --- | --- |
| 이력서 PDF | 통과 | 실패 | 1 / 7 |
| 자기소개서 PDF | 통과 | 통과 | 4 / 4 |
| 포트폴리오 PDF | 통과 | 통과 | 9 / 10 |
| 한국어 PDF | 통과 | 통과 | 1 / 4 |
| 한국어 파서 조각 | 통과 | PDF 미평가 | 1 / 4 |

이력서의 두 열은 추출 단계에서 행 단위로 섞였다. 포트폴리오에서는 PDF 추출 결과에서 들여쓰기가 사라진 코드가 원문 그대로 문단에 남아 코드 참조 점검은 통과하지 않았다. 한국어 정답은 `자기소개서`를 본문 문단으로 두고 `지원동기`를 최상위 제목으로 두지만 모델은 전자를 제목으로, 후자를 그 하위 제목으로 만들었다. 이 관계도 계약상 허용되므로 점수 차이만으로 오류라고 단정할 수 없다. 다만 `지원서 1`은 꼬리말 대신 미배정으로 분류돼 별도 점검이 필요하다. 각 점수는 한 차례의 작은 가상 표본과 명시된 정답 기준의 결과다.

이후 필드나 블록 사이에서 원래 붙어 있던 문자를 나누는 오류도 검증하도록 보강했다. 긴 원문을 호출 크기에 맞춰 단어 중간에서 나눈 경우에는 같은 역할의 인접 문단을 다시 합치고, 안전하게 합칠 수 없으면 원문 대체로 처리한다. 저장된 Luna JSON 다섯 건을 모델 호출 없이 다시 평가했으며 위 필수 검사와 구조 점수는 달라지지 않았다. 이 검사는 긴 문단의 의미적 경계나 올바른 읽기 순서를 보장하지 않는다.

이후 PDF에서 들여쓰기가 빠진 단순 파이썬 함수도 문법으로 확인할 수 있도록 보강한 뒤, 포트폴리오만 Luna로 한 번 호출했다. 결과는 `document_quality_luna_code_result.json`과 `document_quality_luna_code_document.json`에 있다. 코드 참조는 원문 2페이지의 `s13`, `s14`를 가리키며 이 두 조각은 해당 함수의 정의와 반환문이다. 원문은 검증 과정에서 확인하지만 최종 JSON에서 코드 본문을 의도적으로 생략하므로 자동 원문과 숫자 보존 점수는 `null`이며 통과로 계산하지 않는다. 구조 점검은 7 / 10이었다. 두 제목을 문서 제목 아래에 둔 관계는 계약상 가능하지만, 반복된 2페이지 머리말을 제목으로 분류해 정답과 달랐다. 호출은 1회, 입력 1,287토큰과 출력 346토큰이며 일반 요금 기준 약 0.0003달러다. 실제 청구액은 확인하지 못했다.

## 원문 위치 지정 실험

`document_quality_positions.py`는 평가 전용이다. 모델이 원문 조각 ID와 문자 범위를 내면 코드가 해당 범위에서 문자를 가져온다. 각 비공백 문자의 위치가 원문 순서대로 정확히 한 번 사용됐는지 검사해 같은 내용의 중복, 누락과 잘못된 위치를 거부한다. 문단과 제목, 목록 항목 및 표 셀을 지원하고 기존 JSON과 출처 검사를 다시 적용한다. 같은 원문 조각 안의 여러 범위는 원래 사이 공백을 보존하므로 나눈 URL에 임의 공백을 넣지 않는다. 다른 조각을 합칠 때는 공백 한 칸을 넣으므로 줄바꿈이 단어 중간에 있었는지 판정하지 못한다. URL처럼 보이는 문자열이 조각 끝에서 다음 조각과 합쳐질 때는 임의 공백으로 주소를 손상하지 않도록 거부한다. 이미 완결된 URL 다음의 별도 줄도 거부할 수 있는 보수적인 검사다. 모든 위치를 순서대로 사용했더라도 표의 셀 경계가 올바른지는 이 검사만으로 보장하지 않는다. 코드 참조, 자동 줄바꿈과 벌어진 자간의 복구는 구현하지 않았다. 따라서 이 실험은 모든 요구를 만족하는 구현이 아니다.

같은 가상 입력과 Luna 설정에서 한 번 평가한 결과는 `document_quality_model_positions.json`이다. 이력서 1 / 7, 자기소개서 2 / 4, 포트폴리오 0 / 10, 한국어 PDF 3 / 4, 한국어 파서 조각 3 / 4였다. 포트폴리오는 두 번 시도 후 원문 대체됐고 나머지는 한 번씩 구조화됐다. 원문 위치 방식도 두 열 이력서의 읽기 순서는 고치지 못했다. 포트폴리오 거부의 세부 범주를 이 실행에서 기록하지 않아 원인을 확정하지 않는다.

같은 조건의 기존 방식과 비교하면 이력서와 자기소개서 구조 점검이 낮고 한국어는 한 항목 높았다. 코드 참조 미지원과 단일 실행 때문에 효과를 일반화할 수 없다. 현재 실험은 운영에 채택하지 않는다. 재현하려면 위 모델 평가 명령 끝에 `--positions`를 붙인다.

### 동일 모델 재비교

위 최초 위치 실험은 평가기 수정 전의 기록이다. 범위 사이 공백 처리와 평가기를 고친 뒤 같은 가상 자료를 Luna로 각각 한 번 다시 평가했다. 기존 방식과 위치 방식은 결과를 재사용 가능한 JSON으로 저장했고, 최종 평가기로 추가 모델 호출 없이 재채점했다.

| 사례 | 기존 방식 | 위치 방식 | 위치 방식 결과 |
| --- | --- | --- | --- |
| 이력서 | 1 / 7 | 0 / 7 | 두 번 시도 후 원문 대체, PDF 순서 실패 |
| 자기소개서 | 4 / 4 | 3 / 4 | 구조화 |
| 포트폴리오 | 9 / 10 | 0 / 10 | 두 번 시도 후 원문 대체 |
| 한국어 PDF | 1 / 4 | 2 / 4 | 구조화 |
| 한국어 파서 조각 | 1 / 4 | 0 / 4 | 구조화 |

기존 방식은 총 6회, 위치 방식은 총 7회 호출했다. 위치 방식의 입력은 6,083토큰, 출력은 1,725토큰이며 일반 요금 기준 추정치는 약 0.0015달러다. 실제 청구액은 확인하지 못했다. 문서별 호출과 시간, 토큰은 `document_quality_luna_positions_current.json`, 평가 당시의 검증 결과는 `document_quality_luna_positions_documents.json`, 최신 평가기 재채점은 `document_quality_luna_positions_rescored.json`에 있다. 이번 실행의 위치 오류는 세부 범주가 기록되기 전이라 원인을 확정할 수 없다. 결과는 단일 실행이고 위치 방식은 코드 참조를 지원하지 않으므로 공정한 장기 성능 평가가 아니다. 현재 근거로는 운영에 채택하지 않는다.

## 검색 후보 비교

같은 가상 PDF 세 건에 대해 저장된 Luna 구조화 결과와 파서 원문 대체 결과를 각각 별도 범위에 인덱싱하고, 로컬 임베딩 서비스로 네 가지 검색어를 비교했다. 재현 명령은 `uv run pytest -s -q tests/eval/document_quality_retrieval_eval.py`이며 실행 중인 로컬 서비스와 Docker가 필요하다. 실제 지원자 자료나 외부 모델은 사용하지 않았다. 서비스의 모델 버전은 확인할 수 없어 운영 임베딩 모델의 성능으로 일반화하지 않는다.

| 검색어 | 기대 문서 | 구조화 결과 후보 | 원문 대체 결과 후보 |
| --- | --- | --- | --- |
| Python | 이력서 | 이력서, 자기소개서, 포트폴리오 | 이력서, 자기소개서, 포트폴리오 |
| booking process | 자기소개서 | 이력서, 자기소개서, 포트폴리오 | 이력서, 자기소개서, 포트폴리오 |
| Latency | 포트폴리오 | 이력서, 자기소개서, 포트폴리오 | 이력서, 자기소개서, 포트폴리오 |
| quantum cryptography | 없음 | 이력서, 자기소개서, 포트폴리오 | 이력서, 포트폴리오 |

이 표는 근거 재확인 전 후보이며 최종 검색 답변의 정확도를 측정하지 않는다. 관련 문서 세 건은 모두 검색됐지만 무관한 후보가 많았다. 검색 단계는 유사도 기준을 넘은 후보를 개념별 적중 수로 정렬하며, 이후 Root가 근거를 모델로 재확인한다. 구조화와 원문 대체의 우열이나 적절한 유사도 기준은 이 작은 표본만으로 판단할 수 없다. 이번 시험에서는 두 방식 모두 검색 문장의 출처가 지정된 기업과 채용, 지원자 범위에 속하는지 검사했다.

## PDF 글자 간격 실험

가상 PDF에서 글자 간격 설정으로 만든 제목과 실제 공백 문자를 넣은 제목은 파서 결과가 같아도 PDF 글자 목록으로 구분됐다. 그러나 별도로 위치시킨 정상적인 두 단어도 PDF 글자 목록에 공백 문자가 없었다. 한국어 가상 PDF의 벌어진 제목에는 실제 공백 문자들이 포함됐다. 따라서 공백 문자의 존재나 부재만으로 자간과 정상 띄어쓰기를 안전하게 구분할 수 없으며 이 정보만으로 운영 텍스트를 변경하지 않았다. 재현 검사는 `PdfTextTests`에 있다. 현재 정제는 두 칸 이상인 자간을 정리할 수 있지만 한 칸씩 벌어진 제목은 원래 단어 구분을 훼손하지 않도록 보존한다.
