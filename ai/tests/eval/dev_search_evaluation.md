# 개발 환경 가상 지원자 검색 평가

개발 DB의 결제 플랫폼 백엔드 개발자 채용에서 가상 지원자 64명의 제출 문서와 저장된 프로필을 가져온 평가 자료다. `dev_search_dataset.json`에는 연락처 필드를 넣지 않았고 문서 본문의 이메일과 전화번호도 가렸다. DB의 다른 채용과 연락처 정보는 포함하지 않았다.

- 지원자 64명 중 63명은 문서 본문이 있고 한 명은 본문이 비어 있다.
- 스냅샷 당시 프로필이 저장된 지원자는 이재희 한 명이며 항목은 지원서 분석 32개다.
- 평가 또는 면접 분석 프로필 항목은 없었다. 실제로 없는 항목은 평가 자료에 생성하지 않았다.
- 프로필 항목의 내용, 근거, 출처 및 확인 상태는 저장된 값이다. 문서에서는 연락처만 가렸다.

`dev_search_cases.json`은 원문에서 확인한 포함 및 제외 사례다. 전체 64명의 모든 정답을 판정한 목록이 아니므로, 기재되지 않은 지원자를 반환해도 오탐으로 자동 분류하지 않는다. `test_dev_search_eval.py`는 근거 문장이 실제 문서에 있는지 검사하고, 현재 후보 검색의 동일 입력 반복 결과를 검사한다.

## 실행 방법

```bash
cd ai
UV_CACHE_DIR=/tmp/hiremate-uv LANGSMITH_TRACING=false uv run pytest -q tests/eval/test_dev_search_eval.py
```

Docker가 필요하다. 실제 모델로 Root를 평가하려면 모델 설정 후 아래 명령을 실행한다. 가상 지원서 본문이 설정된 모델 제공자에게 전달된다. 검색 조건, 후보, 최종 결과와 지정된 사례의 누락 여부, 시간을 세 번씩 출력한다. 최종 결과의 이름만으로 근거 적합성을 확인할 수는 없다.

```bash
UV_CACHE_DIR=/tmp/hiremate-uv LANGSMITH_TRACING=false LLM_EVAL=true uv run pytest -s -q tests/eval/test_dev_search_eval.py
```

이 평가는 문서와 프로필 스냅샷을 테스트 DB에 넣고 지원자 목록을 재구성한다. 실제 개발 화면의 선택 영역, 전형 상태, 점수와 대화 기록은 재현하지 않는다. 모든 지원자가 검색 가능한 상태이며 각 요청은 독립적으로 실행된다.

## 현재 검색 측정

2026-11-03, `gpt-6-luna`, temperature 0으로 각 질문을 세 번씩 실행했다. 전체 검색 조건과 후보 순서, 최종 결과 및 시간은 `dev_search_baseline.txt`에 있다.

- PG사 9곳 연동: 이재희가 검색 후보에는 포함됐지만 세 번 모두 최종 결과에서 빠졌다. 이 평가의 이름순 목록에서 이재희는 후보 39번째이며, 현 코드의 재확인 상한은 앞 30명이다.
- 결제 실무: 이재희가 후보에 포함됐으나 세 번 모두 최종 결과에서 빠졌다. 모의 결제 프로젝트만 한 이도윤은 최종 결과에 포함되지 않았다.
- 정산 배치: 강준서는 세 번 모두 최종 결과에 포함됐다.
- Kafka 장애 전파: 박재현은 세 번 모두 후보에 포함됐으나 최종 결과에서 빠졌다. 다른 최종 지원자 중 한 명은 마지막 반복에서 달라졌다.

이름순 후보 목록은 스냅샷 재구성의 결과이며 실제 화면의 순서가 아니다. 지정된 사례만 점검했기 때문에 전체 검색률이나 전체 오탐률로 해석하지 않는다. 특히 30명 상한의 영향과 근거 재확인 결과는 별도로 검토해야 한다.
