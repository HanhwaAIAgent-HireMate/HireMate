# 서류 전형 데모

더미 공고(자격요건 5 · 우대사항 5)와 가상 지원자 30명(`applicants.json`)으로 Application Agent의 서류 평가를
스토리보드 v8의 서류 전형 화면(STG-01 · STG-06)에서 확인한다. 지원자는 모두 가상 인물이다.
채점 정답이 있는 서류 평가 데이터셋과 일관성 측정은 [fixtures/README.md](fixtures/README.md)에 있다.

| 무엇 | 어디 |
|---|---|
| 평가 항목(자격요건 5 · 우대사항 5)의 유형 · 중요 표시 · 충족 / 부분 충족 / 미충족 기준 · 선발 인원(1명) | `backend/src/main/resources/application.yml`의 `hiremate.dummy.screening-rubric` |
| 공고 본문 | `seed.py`의 `POSTING`. 자격요건 · 우대사항 글은 위 설정과 같아야 짝이 맞는다 |
| 지원자 | `applicants.json`. `note`는 어떤 경우를 보려는 지원자인지 적은 것이고 제출하지 않는다 |
| 자기소개서 | 문항 3개(지원 동기 700자 · 직무 경험과 본인 역할 1,000자 · 협업 · 문제 해결 700자). 각 지원자의 이력서 · 포트폴리오에 있는 사실만으로 늘려 썼고, 일부러 비워 둔 경험(테스트 코드 등)은 넣지 않았다 |

## 순서

```bash
# 1. DB · Redis (저장소 루트)
docker compose up -d

# 2. ai 스키마. NCS 능력단위 적재(ncs_load.py)는 평가 기준 초안을 쓸 때 참고하는 자료라 서류 평가에는 없어도 된다
cd ai
uv run alembic upgrade head
uv run python scripts/ncs_load.py

# 3. ai 서버. ai/.env에 모델 연결을 넣는다 (ai/.env.example). 실제 지원자 정보는 외부 API로 보내지 않는다.
#    OpenAI로 볼 때는 LLM_MODEL=gpt-4.1-mini, LLM_STRUCTURED_OUTPUT=function_calling으로 둔다. json_schema에서는
#    일부 이력서에서 모델이 탭을 끝없이 써 출력 한도에 걸리고, 같은 질문이라 다시 물어도 똑같이 실패했다.
#    Windows에서는 --reload로 띄운다 (psycopg 비동기 연결이 기본 이벤트 루프에서 동작하지 않는다)
uv run uvicorn hiremate_ai.main:app --port 8001 --reload --reload-dir src

# 3-1. AI 워커 (ai 폴더, 다른 터미널). 지원서 분석 작업을 대기열에서 하나씩 꺼내 처리한다.
#      로컬 모델은 지원자 한 명에 몇 분 걸리므로 APPLICATION_TIMEOUT_SECONDS를 늘린다
uv run python -m hiremate_ai.worker

# 4. backend. 지원서 분석은 대기열로 AI 워커에, 카드 분석은 ai 서버로 보낸다
cd backend
HIREMATE_AI_AGENTS_APPLICATION=remote HIREMATE_AI_AGENTS_CANDIDATE_ANALYST=remote ./gradlew bootRun

# 5. frontend
cd frontend && npm run dev

# 6. 데모 데이터 (저장소 루트). 가입 · 로그인, 공고 게시, 지원서 제출, 접수 마감까지 한다
uv run scripts/demo/seed.py --email demo-hr@example.com --password <12자 이상>
```

마지막에 나오는 서류 전형 화면 주소를 열고 같은 이메일로 로그인한다.

## 화면에서 볼 것

- 서류 평가 점수 = 자격요건 50점 + 우대사항 50점 (우대사항이 없으면 자격요건이 100점). 소수 첫째 자리까지 보인다.
  - 영역 점수 = 영역 만점 × Σ충족도 ÷ 항목 수. 영역 안의 항목은 모두 같은 비중이다 (중요 표시는 점수에 쓰지 않는다).
  - 충족도: 충족 1 · 부분 충족 0.5(복합 경험형만) · 미충족 0. 조건형 · 단일형에 부분 충족이 나오면 받지 않는다.
  - 항목마다 업무 관련성 · 본인 역할 · 수행 범위 · 원문 근거를 보고 충족도 하나를 정한다. 따로 점수를 더하지 않는다.
  - 경력 'N년 이상'은 요건의 직무 · 기술에 해당하는 재직 기간만 코드가 더한다. 근무 기간을 찾지 못하면 신입이 아니라
    `경력 확인 필요`다. 자격증 조건은 코드가 이름으로 확인하고 확인 상태(본인 기재 · 증빙 제출)를 남긴다.
- 확인 필요(UNKNOWN) 항목은 1차(주변 문맥 · 본인 역할) · 2차(다른 제출 문서)로 다시 판정한다 (항목마다 최대 2번,
  분석 한 번에 150초 안). 그래도 남으면 총점을 보류한다. 보류 지원자는 확인 필요를 0점으로 계산한 점수가 회색으로
  `보류 45.8`처럼 보이고(연한 회색 행), 카드에 보류 이유가 나온다. 서류를 읽지 못한 지원자는 `보류 0.0`이다.
- 리스트는 처음에 자격요건 점수 순(같으면 총점 순)이고, `총점 순`으로 바꿔 볼 수 있다. 보류 지원자도 그 점수로
  같은 줄에 선다. 선발 인원 1명 × 10 = 상위 10명이 AI 추천으로 굵게 보이고(끝 순위가 공동이면 모두),
  나머지는 회색이다 (스토리보드 COM-02 · STG-01). 경력 줄 아래에 `자격 37.5 · 우대 40.0`이 작게 붙는다.
- 자격요건 75% 통과는 점수와 따로 센다 (부분 충족은 0.5개, 확인 필요 때문에 결과가 갈리면 판단 보류).
  하나라도 못 채운 자격요건은 점수가 높아도 이름 옆에 `✕ 신입`처럼 붙는다. 불합격 표시가 아니다.
- 지원자를 누르면 AI 분석이 요약(점수 · 항목별 판정 칩 · 눈여겨볼 점 · 확인 필요 2개씩)으로 나온다. `자세히`를 누르면
  항목별 판정 · 획득 점수 / 배점 · 이유 · 충족 / 미충족 부분 · 확인 경력 · 출처 · 평가 기준 버전이 나온다. 공고 조건에 대한 서류 평가일 뿐 합격 여부가 아니다.
- 한예린의 포트폴리오에 든 평가 조작 문장은 따르지 않는다.

## 분포 리포트 데모 (지원자 수백 명)

리포트 창의 `분포`를 보려면 지원자가 많아야 한다. 실제 모델로 수백 명을 분석하면 몇 시간이 걸리므로 backend를
Application Agent stub(기본값, `HIREMATE_AI_AGENTS_APPLICATION`을 주지 않는다)으로 띄우고 `seed_many.py`를 쓴다.
ai 서버 · 워커는 분포에는 필요 없고, 분포에서 `심층 분석`(비교 리포트)을 Report Agent로 쓰려면 띄운다.

```bash
# 1 · 4 · 5번은 위와 같다 (backend는 stub 그대로 ./gradlew bootRun)
uv run scripts/demo/seed_many.py --count 300 --headcount 6 --email demo-hr@example.com --password <12자 이상>
```

- 지원자는 `applicants.json` 30명의 문서에서 줄을 지원자마다 다르게 뺀 가상 인물이다. 같은 `--seed`면 같은 지원자다.
- stub은 평가 항목 글의 낱말이 문서에 나오는 비율로 항목마다 판정한다(60% 이상 충족, 복합 경험형 30% 이상 부분 충족,
  조금이라도 나오면 확인 필요, 없으면 미충족). 분포 화면을 보려는 개발용 값이고 실제 판정은 ai 서버가 한다.
- 공고 채용 인원(`--headcount`) × 10이 분포의 서류 통과 목표 기본값이다. 화면에서 바꿀 수 있고 저장하지 않는다.
- 선택 지원자 칸의 `리포트 생성`을 아무도 체크하지 않고 누르면 분포가, 2~5명을 체크하고 누르면 심층 분석이 먼저 열린다.
- 경계 기준(선 아래 다시 볼 사람의 필수 조건 개수, 심층 분석 인원, 목표 배수)은 `backend/src/main/resources/application.yml`의
  `hiremate.report.distribution`에 있는 임시값이다.

## 운영 기준점 (시연 데이터 되돌리기)

운영(https://hiremate.yuumin.com)의 데이터를 정해 둔 기준점으로 언제든 되돌린다. 시연이나 테스트로 결정 · 선택 ·
Chat 기록이 바뀌어도 한 번 실행하면 기준점의 채용 진행 상태와 AI 분석 결과로 돌아온다. LLM을 다시 부르지 않는다.

### 실행

GitHub Actions 탭 → **demo baseline** → **Run workflow**에서 고른다. `main` 브랜치에서만 돈다.

| action | 하는 일 |
|---|---|
| `restore` | 기준점으로 되돌린다. 서비스가 1~2분 멈추고 접속한 모든 사람이 로그아웃된다 |
| `snapshot` | 지금 상태를 새 기준점으로 뜬다. 이전 기준점은 최근 5개까지 서버에 남는다 |
| `status` | 기준점 목록을 본다 |

운영 DB를 통째로 바꾸므로 `confirm` 칸에 action과 같은 낱말(`restore` 등)을 적어야 실행된다. 터미널에서는 이렇게 부른다.

```bash
gh workflow run demo-baseline.yml -f action=restore -f confirm=restore
```

### 되돌리는 범위

- DB 전체: backend `public` 스키마(회사 · 계정 · 채용 · 전형 · 지원서 · 결정 이력)와 `ai` 스키마(분석 결과 · 지원자 프로필 ·
  검색 색인 · Chat 대화방). 두 스키마를 지우고 다시 만들므로 기준점 이후에 생긴 계정, 채용, 기록과 표는 모두 사라진다.
  한 트랜잭션이라 복원에 실패하면 DB는 그대로다.
- 지원자 서류(PDF)는 비공개 S3에 있고 지우지 않으므로 그대로 이어진다. S3에서 서류를 지우면 그 전에 뜬 기준점은 쓰지 못한다.
- Redis(로그인 세션, 작업 대기열)는 비운다.
- 기준점 이후 배포로 스키마가 바뀌었으면 복원 뒤 최신으로 올린다(backend Flyway는 시작할 때, ai는 `alembic upgrade head`).
